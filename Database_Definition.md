# BioScope Database Definitions

This document is a simple, client-friendly explanation of the main database tables used in the BioScope platform.

It is intended for sharing with non-technical stakeholders who need to understand what information the system stores.

---

## 1. actuators

Stores the output devices that BioScope can control.

Examples:
- Fan
- Heater
- Light

Main details stored:
- Which device the actuator belongs to
- The actuator name and type
- Whether it is currently ON or OFF
- The current control value
- Whether automation is allowed to control it
- Which physical slot it is connected to

---

## 2. alert_rules

Stores the definitions of alert conditions.

Examples:
- High temperature alert
- Low humidity alert
- Device offline alert

Main details stored:
- Rule name and description
- Which device the rule applies to
- The condition that triggers the alert
- Severity level
- Notification channels
- Whether the rule is active

---

## 3. alerts

Stores actual alert events generated by the system.

Examples:
- Temperature exceeded safe range
- Device stopped sending data

Main details stored:
- Which rule triggered the alert
- Which device is affected
- Alert severity and title
- When the alert was triggered
- Whether it has been resolved
- Who acknowledged or resolved it

---

## 4. audit_log

Stores a history of important system and user actions.

Examples:
- User changed a device setting
- Automation triggered an actuator
- A record was updated or deleted

Main details stored:
- Who performed the action
- Which device or record was affected
- What action happened
- Old and new values
- Action status
- Timestamp of the event

---

## 5. automation_rules

Stores the rules used for automatic environmental control.

Examples:
- Turn fan ON if temperature is too high
- Turn heater ON if temperature is too low
- Turn light OFF at a certain threshold

Main details stored:
- Rule name and description
- Target parent device
- Trigger condition
- Action to perform
- Whether the rule is active
- How many times the rule has run
- Last time the rule was triggered

---

## 6. child_units

Stores the individual growing chambers or controlled units connected under a main parent unit.

Examples:
- Chamber C1
- Chamber C2

Main details stored:
- Unit ID and name
- Parent unit relationship
- Location
- Priority level
- Online or offline status
- Creation date

---

## 7. control_actions

Stores every control action sent to actuators.

Examples:
- User turned fan ON manually
- Automation turned heater OFF

Main details stored:
- Which device and actuator were targeted
- Whether the action was manual or automatic
- Previous and new state
- Reason for the action
- Rule or user that triggered it
- Result status
- Timestamp

This table also keeps the latest logical states for fan, heater, and light.

---

## 8. control_history

Stores a simplified history of control commands for reporting and display.

Examples:
- Fan ON
- Heater OFF

Main details stored:
- Device ID
- Actuator name
- Command sent
- Whether it was manual or automatic
- Success or failure status
- Timestamp

---

## 9. device_settings

Stores configuration settings for each parent device.

Examples:
- Polling interval
- Timezone
- Relay slot assignments

Main details stored:
- Device ID
- Polling and retention settings
- Timezone
- Coordinates
- Slot 1 assigned device
- Slot 2 assigned device
- Extra metadata

This table defines which physical relay slot controls fan, heater, or light.

---

## 10. devices

Stores a general list of registered devices in the system.

Examples:
- Parent units
- Child units

Main details stored:
- Device ID
- Device name
- Device type
- Status
- Location
- Creation date

---

## 11. parent_units

Stores the main control hubs in the BioScope system.

Examples:
- Parent Unit P1
- Parent Unit P2

Main details stored:
- Unit ID and name
- Location
- Gateway information
- Firmware version
- Network type
- Device status
- Control mode

These records are the top-level devices that manage one or more child units.

---

## 12. readings

Stores environmental sensor data collected over time.

Examples:
- Temperature readings
- Humidity readings
- Light readings

Main details stored:
- Device ID
- Sensor ID
- Temperature
- Humidity
- Light level
- Priority level
- Raw sensor payload
- Recorded timestamp

This is the core time-series data table for charts, trends, and analytics.

---

## 13. sensor_types

Stores the list of supported sensor categories.

Examples:
- Temperature
- Humidity
- Light Level
- CO2
- Air Pressure

Main details stored:
- Sensor type name
- Measurement unit
- Minimum value
- Maximum value
- Description

---

## 14. sensors

Stores the physical sensors attached to child units.

Examples:
- Temperature sensor in chamber center
- Light sensor near plant tray

Main details stored:
- Sensor ID
- Device ID
- Sensor type
- Sensor name
- Location
- Whether it is active
- Calibration offset
- Last reading and time

---

## 15. user_preferences

Stores personal settings for each user.

Examples:
- Theme selection
- Notification preferences
- Language and timezone

Main details stored:
- User ID
- Theme
- Notification options
- Dashboard refresh interval
- Timezone
- Language
- Extra settings metadata

---

## 16. users

Stores application user accounts.

Examples:
- Administrators
- Operators
- Standard users

Main details stored:
- User ID
- Email
- Name
- Phone number
- Role
- Active or inactive status
- Account creation date
- Last login time

---

## 17. vw_active_alerts

This is a view, not a physical table.

Purpose:
- Shows all currently unresolved alerts
- Combines alert information with alert rule information

Used for:
- Dashboard alert lists
- Active alerts screen

---

## 18. vw_device_summary

This is a view, not a physical table.

Purpose:
- Provides a quick summary of each device
- Combines device details, latest readings, and current actuator states

Used for:
- Dashboard device cards
- Summary screens

---

## 19. vw_latest_readings

This is a view, not a physical table.

Purpose:
- Shows the most recent reading for each device

Used for:
- Dashboard metrics
- Latest status displays
- Fast access to current environmental values

---

## Simple Relationship Summary

- A parent unit manages one or more child units.
- Child units contain sensors and actuators.
- Sensors generate readings.
- Automation rules decide when actuators should turn ON or OFF.
- Alert rules generate alerts when conditions are outside safe ranges.
- Users can manually control actuators and change settings.
- Audit logs keep a history of important actions.

---

## Client Summary

In simple terms, the BioScope database is organized into five main areas:

1. Device structure
   - `parent_units`, `child_units`, `devices`

2. Environmental data
   - `sensors`, `sensor_types`, `readings`

3. Control and automation
   - `actuators`, `automation_rules`, `control_actions`, `control_history`, `device_settings`

4. Alerts and monitoring
   - `alert_rules`, `alerts`, `vw_active_alerts`

5. Users and system records
   - `users`, `user_preferences`, `audit_log`

This structure allows BioScope to monitor environmental conditions, automate responses, track user activity, and provide reporting for each managed unit.
